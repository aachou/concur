<h1 align="center">多处理器编程的艺术</h1>
<h2 align="center">第六章 共识的通用性 总结</h2>

## 1. 主题与核心思想

第 5 章用共识数证明了"低层对象无法实现高层对象"的**不可能性**，但无等待同步并非不可行——本章反过来证明：**存在通用对象**，只要提供足够数量，就能为**任意**并发对象构造出无等待、可线性化的实现。

- **通用判据**：n 线程系统中，某类对象的共识数 ≥ n 当且仅当它是通用的。
- **CAS 是终极原语**：共识数无限 → 对任意数量线程都通用 → 支持 CAS 的机器能以无等待方式实现任何并发对象。
- 通用层次表（图 6.1）：原子寄存器(1) < getAndSet/getAndAdd/队列/栈(2) < … < (m, m(m+1)/2)-赋值(m) < … < CAS / 存储器—存储器迁移 / LL-SC(∞)。
- **类比经典可计算性理论**：通用构造不是实用工程指南，价值在于让人避免去徒劳地解决本质不可解的问题——先理解共识为何强大，之后再谈工程优化效率。

## 2. 通用性

**定义**：若能用类 C 的若干对象 + 若干读写寄存器，构造出**任意对象**的无等待实现，则称类 C 通用。

- 允许**多个**类 C 对象（机器指令可作用于多个存储单元）；读写寄存器仅做簿记、数量不限（现代体系结构存储器充足）。
- 先做无锁版本，再扩展为无等待版本。

## 3. 无锁的通用构造

**思路**：把串行对象表示为 **"初始串行对象 + 日志"**——日志是一个节点链表，记录作用于对象的方法调用序列（状态转换序列）。

- 串行对象接口：`apply(Invoc) → Response`，且必须是**确定**的（同状态同调用 → 唯一响应和唯一新状态）。
- **核心不变式：只有链表头部可变**——初始状态及头部之后的所有节点一旦创建就永不改变。
- **难点**：共识对象只能用一次（每个线程只能调用一次 decide()），无法用单个共识对象追踪头部 → 仿面包房锁引入**每线程 head[] 数组**：`head[i]` = 线程 i 观察到的最后节点，链表实际头部 = `head[]` 中 seq 最大的节点（max() 即一次收集扫描）。

**apply() 流程**（每线程）：
1. 创建节点封装调用，节点含 `decideNext`（共识对象）、`next`、`seq`。
2. 循环：`before = max(head)` → `after = before.decideNext.decide(prefer)`（竞争新头部）→ `before.next = after` → `after.seq = before.seq + 1` → `head[i] = after`。
3. 创建串行对象私有副本，从链表尾到自身节点依次 apply 每个调用，返回自己的结果。

**关键点**：
- 遍历时所有前置节点的 `next` 必然已设置好——每次添加都通过共识更新前驱的 `next`，可见性有保障。
- **可线性化**：每个 apply() 可在其 decide() 调用生效的时刻线性化。
- **无锁**：每次共识都推进日志，新头部总能在有限步内写入 head[]；唯一阻止某线程加节点的情况是别人不断加——那说明系统整体在前进。

## 4. 无等待的通用构造

**升级**：从无锁到无等待的关键是**互帮互助**——推进中的线程主动帮助未能取得进展的线程完成其调用，保证任何线程不被饿死。

- 引入 n 元数组 `announce[]`：`announce[i]` = 线程 i 当前尝试挂入的节点，宣告即公开，他人可代劳。
- 主循环里每次先决定**该帮谁**：`help = announce[(before.seq + 1) % n]`，若 `help.seq == 0`（需要帮助）就以它为 prefer，否则才推自己的节点。按 seq mod n 递增轮转，保证任何靠自身无法推进的节点终会被帮助。
- **不重复挂载**：节点被两线程先后尝试挂入时，第二次必然失败——该节点 seq 已非零（已写入过 head[]），验证过不了。每节点至多挂载一次，挂载次序与调用自然偏序一致 → **可线性化**。

**无等待证明**（辅助变量 / 幻影变量）：
- `concur(A)` = 自 A 宣告以来被写入 head[] 的节点集合；`start(A)` = A 宣告时 max(head[]) 的 seq。
- 核心不变式：`|concur(A)| + start(A) = max(head[])`。
- 引理 6.4.1：`|concur(A)| > n ⟹ announce[A] ∈ head[]`。因为多于 n 个并发节点中必存在两个连续节点 b、c 使 `(seq+1) mod n` 依次落在 A-1、A 上；挂入 c 的线程 C 在执行帮助逻辑时必已读到 A 的宣告，于是挂入 a。
- 引理 6.4.2–6.4.5 递推：`max(head[]) ≥ start(A)`；`head[A].seq ≥ start(A)`（第 15/26 行赋值保证）；`|concur(A)| ≥ head[A].seq - start(A) ≥ 0`。
- 定理 6.4.6：线程 A 主循环至多执行 n+1 次（每次成功迭代 `head[A].seq` 加 1）；n+1 次后 `|concur(A)| ≥ n`，由引理 6.4.1 得 `announce[A]` 已入 head[] → **无等待**。

### 正确性论证（线性一致性）

每个 apply 包装成一个节点，各链位由共识决出胜者挂入链表，线性点即节点挂入时刻。挂入顺序对所有 apply 构成全序，且不重叠调用中先完成者必先挂入，故与实时次序一致。因链表前缀一经创建永不改变，且串行对象确定，从初始状态沿链重放等价于在前驱状态上顺序执行当前调用，响应符合顺序规约 → 链中序列为合法顺序历史，即线性一致性。

## 5. 核心收获

- **共识数 = 通用性的门票**：共识数 ≥ n 的对象能构造任意 n 线程对象的无等待实现；共识数不足则（第 5 章）连特定对象都造不出。CAS（∞）因此是"万物之王"。
- **两个通用构造范式**：① **日志链表式**——把并发方法调用序列化为有序链表，只让头部可变；② **宣告 + 帮助**——announce[] 数组 + seq mod n 轮转，把无锁升级为无等待、防止饿死。"帮助"范式会反复出现在后续无等待算法中。
- 理解通用构造的**存在性**（类比丘奇-图灵），避免在不可解问题上浪费时间，再谈工程化效率优化。
