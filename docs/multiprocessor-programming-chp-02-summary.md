<h1 align="center">多处理器编程的艺术</h1>
<h2 align="center">第二章 互斥 总结</h2>

## 1. 时间和事件

为精确描述并发行为，引入形式化的事件模型：

- **事件**：瞬时发生（不占时间），不同事件的时间戳互不相同
- **先于关系** →：事件集合上的**全序关系**
- **时间间隔** I = (a₀, a₁)：两个事件之间的持续时间
- **间隔偏序**：I~A~ → I~B~ 当且仅当 a₁ → b₀；重叠的间隔称为**并发**（无 → 关系）

该模型为后续所有算法的正确性证明提供统一的叙述语言。

## 2. 临界区与锁

共享计数器 `value++` 实际拆分为读→改→写三步，多线程并发导致数据竞争。

解决方案：**临界区**（critical section）——一次只允许一个线程执行的代码块。

**Lock 接口**：

```java
public interface Lock {
    public void lock();    // 进入临界区前调用
    public void unlock();  // 离开临界区前调用
}
```

**三个核心特性**：

| 特性 | 类型 | 含义 |
|------|------|------|
| **互斥** | 安全特性 | 最多一个线程持有锁 |
| **无死锁** | 活跃特性 | 若某线程永远无法获得锁，则必有其他线程在反复进出临界区 |
| **无饥饿** | 活跃特性 | 每个试图获取锁的线程最终都会成功（蕴含无死锁） |

## 3. 双线程互斥算法

### 3.1 LockOne（标志法）

每个线程设置自身 flag，等待对方 flag 为 false。

- **互斥** ✓（可通过 → 运算反证法证明）
- **无死锁** ✗：若两线程同时设置 flag，则互相永久等待

### 3.2 LockTwo（受害者法）

每个线程将 victim 设为自己，等待 victim 变为对方 ID。

- **互斥** ✓
- **无死锁** ✗：除非两线程同时运行（并发），否则不会成功

### 3.3 Peterson 锁

**结合 LockOne + LockTwo**，消除各自的死锁场景：

```
flag[i] = true;          // 我感兴趣
victim = i;              // 你先运行
while (flag[j] && victim == i) {}  // 等待
```

核心思想：先声明意图（flag），再谦让（victim）。若对方也在竞争，victim 必会变为对方，从而通过等待条件。

- **互斥** ✓
- **无饥饿** ✓
- **无死锁** ✓

彼得森算法是最简洁优雅的双线程互斥算法。

## 4. 死锁与活锁

使用多个锁的程序可能出现另一种死锁：线程 A 持有锁 L₀ 并等待 L₁，线程 B 持有锁 L₁ 并等待 L₀——双方互相等待对方释放锁。这类死锁并非算法本身的缺陷，而是锁使用顺序不当所致。

| 概念 | 行为 | 示例 |
|------|------|------|
| **狭义死锁** | 线程停滞等待，无法继续 | LockOne 双方在 while 中永等 |
| **活锁** | 线程持续运转但互相抵消，无进展 | 双方都执行鲍勃策略，flag 交替设置/清除 |

书中定义的**无死锁特性**同时排除了狭义死锁和活锁。

## 5. 过滤锁（Filter Lock）

**Peterson 锁的 N 线程泛化**。构造 n-1 个级别，每个线程须逐级通过：

- level[A]：线程 A 当前所处的级别（0 表示没有尝试获取锁）
- victim[L]：每个级别 L 对应一个 victim，用于"过滤"出一个线程

**关键特性**：

- 至少有一个线程能成功进入级别 L
- 若多个线程试图进入级别 L，则至少有一个被阻塞

最终，最多只有一个线程能到达最高级别 n-1（即进入临界区）。

## 6. 公平性

无饥饿不保证先到先服务。为定义公平性，将 `lock()` 分为两段：

| 阶段 | 特性 | 步骤数 |
|------|------|--------|
| **入口区（doorway）** | 有界无等待 | 有限步数内完成 |
| **等待区（waiting）** | 可能无限循环 | 可能无限步 |

**先到先服务**（FCFS）：若线程 A 在 B 之前完成入口区，则 A 先于 B 进入临界区。满足无死锁 + FCFS 的算法必然满足无饥饿。

## 7. 面包房锁（Bakery Lock）

**分布式取号机**，实现 FCFS 公平性：

```
flag[i] = true;
label[i] = max(label[0], ..., label[n-1]) + 1;   // 入口区（有界无等待）
while (∃k: flag[k] && (label[k], k) << (label[i], i)) {}  // 等待区
```

字典序 `(label[k], k) << (label[i], i)`：
- `label[k] < label[i]`，或
- `label[k] == label[i]` 且 `k < i`

**关键洞察**：入口区中读取标签集并非原子操作（可能读到从未同时存在的标签组合），但算法仍然正确。

## 8. 有界时间戳

面包房锁的 label 无限增长 → 长时间运行可能溢出。

**时间戳系统**提供两种能力：

- **扫描**（scan）：读取所有线程的时间戳
- **标记**（label）：为自己分配一个更晚的时间戳

串行时间戳系统（扫描 + 标记原子执行）是理解并发时间戳系统的理论基础。

## 9. 存储单元下界

任何基于普通**读/写指令**（load/store）的 N 线程无死锁互斥算法，至少需要 **n 个不同的存储单元**。

**证明思路**：读写的根本限制在于——一个线程写入存储单元的数据在另一个线程读取前可能被覆盖。通过分析系统状态的覆盖关系，可以证明 n 个线程的互斥需要至少 n 个存储单元。

**结论意义**：这一下界促使多处理器硬件引入比普通读/写指令更强的同步操作（如读取-修改-写入指令），从而在设计实用互斥算法时突破该限制。

## 10. 总结

第二章从理想化模型出发，系统性地构建了对互斥问题的完整理解：

1. **形式化基础**：事件 → 偏序 → 时间间隔，为证明提供精确语言
2. **从双线程到 N 线程**：LockOne → LockTwo → Peterson（双线程）→ Filter Lock（N 线程，无饥饿但不公平）→ Bakery Lock（N 线程，FCFS 公平）
3. **特性层次**：互斥（安全）→ 无死锁（活跃）→ 无饥饿（更强活跃）→ FCFS 公平性
4. **理论边界**：实现 N 线程无死锁互斥需要的读/写存储单元的下界为 n，解释了为何实际算法需要更强硬件原语
5. **实践启示**：本章算法（除面包房锁）在现代架构中虽不实用，但对同步领域的算法设计与正确性证明的训练至关重要——同样的推理方法在后续章节的实用算法中反复出现。

> 本章是全书中为数不多包含完整数学证明的章节，其核心价值不在于算法本身，而在于**如何推理并发算法的正确性**——这种能力是学习更复杂同步机制（自旋锁、管程、事务性内存）的基石。
