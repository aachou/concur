## 1. 引言

在第 5 章中，我们介绍了一种简便的证明方法，用于判定形如“不存在通过 Y 构造 X 的无等待的实现”的命题。接下来，针对具有确定性串行规范的对象类，我们构建了一个层次结构（见图 6.1），其中低层对象无法用于实现高层对象。每个对象都有一个关联的**共识数**，表示该对象可以解决共识问题的最大线程数。在包含不少于 n 个并发线程的系统中，无法利用共识数小于 n 的对象，构造出共识数为 n 的对象的无等待（或无锁）实现。此后，除非特别说明，所有适用于无等待实现的结论，同样适用于无锁实现。

第5章的不可能性结论，并不意味着无等待同步本身不可行或无法实现。事实上，本章将证明存在一些**通用**（universal）对象：只要提供足够数量的这类对象，就能为任意并发对象构造出一种无等待且可线性化的实现。

在一个包含 n 个线程的系统中，当且仅当某个类的共识数大于或等于 n 时，该类才是通用的。在图 6.1 中，第 n 层的类对于一个包含 n 个线程的系统是通用的。一种机器体系结构或程序设计语言，当且仅当它能够以通用类的对象作为操作原语时，才具备支持任意无等待同步的计算能力。例如，现代多处理器提供的 `compareAndSet`（CAS）指令，其共识数为无限大，因此对于任意数量的线程都是通用的。搭载该指令的机器，便能够以无等待的方式实现任何并发对象。

| ------ | --------------------------------------------------- |
| 1      | 原子寄存器                                          |
| 2      | getAndSet、getAndAdd、Queue、Stack                  |
| …      | …                                                   |

本章主要阐述如何使用共识对象来实现并发对象的**通用构造**（universal construction）。需要说明的是，这并非实现无等待对象的实用技术指南。与经典的可计算性理论一样，理解通用构造及其本质含义，可以帮助我们避免犯下那些试图解决本质不可解问题的幼稚错误。一旦理解了共识为何如此强大——足以实现任意类型的对象——我们便可以在此基础上通过工程实践不断优化其效率。

## 2. 通用性

如果可以使用类 C 的若干对象以及若干读写寄存器，构造出任意对象的无等待实现，则称类 C 是通用的。构造中允许使用多个类 C 的对象，是因为我们关注的是机器指令的同步能力，而大多数机器指令也确实可以作用于多个存储单元。允许使用多个读写寄存器，是因为它们仅用于簿记，且现代体系结构通常提供大量存储器。为了避免无关细节的干扰，我们对所使用的共识对象数量和读写寄存器数量均不作限制；存储单元的回收问题则留给读者自行考虑。本章先从无锁实现入手，再将其扩展为稍复杂的无等待实现。

## 3. 无锁的通用构造

图 6.2 给出了串行对象的**通用**（generic）定义，它基于第 3 章中调用-响应的表达方式。每个对象都从某个固定的初始状态开始。其 `apply()` 方法接受一个调用（invocation）作为参数，该调用描述了要执行的方法及其参数；方法返回一个响应（response），包含调用的终止状态（正常或异常）以及可能的返回值。例如，对栈对象调用 `push()` 方法并传入一个参数，其对应的响应是一个正常终止状态且无返回值。

```java
public interface SeqObject {
    public abstract Response apply(Invoc invoc);
}
```

<p align="center">图 6.2 一个通用的串行对象：apply() 方法执行调用并返回一个响应</p>

图 6.3 和图 6.4 给出了一种通用构造，可将任意串行对象转换为无锁且可线性化的并发对象。该构造要求串行对象是**确定的**：对处于特定状态的对象调用一个方法，只能产生唯一的响应和一个唯一的新状态。

该构造将对象表示为“初始串行对象 + 日志”的组合，其中日志是一个由节点组成的链表，记录了作用于该对象上的方法调用序列（即状态转换序列）。线程执行方法调用时，先将新调用封装为节点并添加到链表头部，随后从链表尾部向头部遍历，依次将各调用应用到对象的私有副本上，最后返回自身调用的执行结果。

这里的关键在于：**只有链表的头部是可变的**——初始状态以及头部之后（更靠近尾部）的所有节点一旦被创建就永远不会改变。

```java
public class Node {
    public Invoc invoc;					// 方法名称及参数
    public Consensus<Node> decideNext;	// 决定链表中的下一个节点
    public Node next;					// 下一个节点
    public int seq;						// 序列号
    public Node(Invoc invoc) {
        invoc = invoc;
        decideNext = new Consensus<Node>();
        seq = 0;
    }
    public static Node max(Node[] array) {
        Node max = array[0];
        for (int i = 1; i < array.length; i++) {
            if (max.seq < array[i].seq)
                max = array[i];
        }
        return max;
    }
}
```

```java
public class LFUniversal {
    private Node[] head;
    private Node tail;
    public LFUniversal() {
        tail = new Node();
        tail.seq = 1;
        for (int i = 0; i < n; i++)
            head[i] = tail;

    public Response apply(Invoc invoc) {
        int i = ThreadID.get();
        Node prefer = new Node(invoc);
        while (prefer.seq == 0) {
            Node before = Node.max(head);
            Node after = before.decideNext.decide(prefer);
            before.next = after;
            after.seq = before.seq + 1;
            head[i] = after;

        Node currenct = tail.next;
        while (currenct != prefer) {
            MyObject.apply(currenct.invoc);
            currenct = currenct.next;
        }
        return myObject.apply(currenct.invoc);
```

<p align="center">图 6.4 无锁的通用构造</p>

如何使基于日志的构造支持并发调用 `apply()` 呢？当某线程调用 `apply()` 时，它先创建一个节点来封装本次调用。随后，所有并发调用线程通过竞争，试图将自己的节点挂入日志链表的头部。这一竞争通过运行一个 n-线程共识协议来实现：协议以各线程的节点引用为输入，输出唯一的获胜节点，该节点将被成功添加到链表头部。

共识胜出的线程随后可计算其响应。它创建一份顺序对象的本地副本，从日志链表的尾部开始，沿 `next` 引用正向遍历至链表头部，依次将各节点的操作应用到本地副本上，最后返回与自身调用对应的执行结果。

即便多个线程并发调用 `apply()`，算法依然正确，因为该线程自身节点之前的所有前缀节点永不改变。那些未能胜出的线程则需要在新一轮竞争中重试——由于当前日志头部可能已被其他线程推进，它们需以新的头部节点作为共识目标再次尝试挂载自己的节点。

接下来我们详细分析无锁通用构造，其代码如图 6.4 所示，图 6.5 则给出了一个执行实例。该构造的核心是一个由节点组成的日志链表，每个节点封装了一个方法调用，节点结构如图 6.3 所示。其中，`decideNext` 字段是一个共识对象，用于决定下一个挂入链表的节点；`next` 字段存储共识协议的结果，即对下一个节点的引用；`seq` 字段表示节点在链表中的序号，尚未挂入时为 0，挂入后为正数，且沿链表方向严格递增。初始状态下，链表中仅含一个序号为 1 的哨兵节点。

在设计并发无锁的通用构造过程中，其难点在于共识性对象只能被使用一次。

> *创建一个可重用的共识性对象，或者即使是一个仅决定值可读的对象，并不是一项简单的任务。其实质与我们将要设计的通用构造基本上是同一个问题。例如，考虑 5.4 节中基于队列的共识性协议。在共识性对象状态被决定之后，如何使用一个 Queue 队列来允许重复读取共识性对象的状态并不是一件很容易的事情。*

![fig1](../static/images/multiprocessor-programming-chp-06/fig1.png)

在图 6.4 的无锁算法中，每个线程创建一个节点来封装其调用，并反复尝试将该节点挂载到日志链表的头部。每个节点含有一个 `decideNext` 字段，类型为共识对象。线程通过将该节点作为输入，提交给当前链表头部节点的 `decideNext` 共识对象，以竞争成为新的头部。所有参与竞争的线程对同一个共识对象进行提议，最终所有线程都会得到相同的获胜节点。该结果被写入前驱节点的 `next` 字段，以便不参与此次共识的线程也能通过链表遍历看到该节点。节点被挂载后，挂载它的线程会为其分配一个全局递增的序号。

一旦某个线程的节点被成功挂入日志链表，该线程便从链表尾部（哨兵节点）开始，沿 `next` 引用正向遍历至自己新增的节点，依次将每个节点中的方法调用应用到对象的私有副本上，最终返回自身调用的执行结果。

需要指出的是，当线程执行这段遍历时，其所有前置节点的 `next` 引用必然已经设置妥当——因为这些节点此前已被添加到链表中，而每次添加操作都通过共识协议更新了前驱节点的 `next` 指针，因此该字段的可见性是有保障的。

日志链表的头部需要持续更新，而每个线程对共识对象的访问次数受限（每个线程只能调用一次 `decide()`），因此无法使用单个共识对象来追踪头部。为此，我们借鉴了面包房锁算法（2.7 节）中的每线程结构，引入一个长度为 n 的 `head[]` 数组，其中 `head[i]` 记录线程 i 当前观察到的链表最后一个节点。初始时，所有 `head[i]` 均指向哨兵节点 `tail`。链表的实际头部被定义为 `head[]` 数组中序号最大的那个节点。图 6.3 中的 `max()` 方法执行一次收集操作，扫描整个 `head[]` 数组并返回其中序号最大的节点。

该构造是串行对象的一种可线性化实现。每个 apply() 方法的调用都可以利用 decide() 方法的调用将节点添加到日志链表中的时间点线性化。

这个构造是无锁的，原因在于日志链表的头部（即最新节点）总能在有限步数内被写入 `head[]` 数组中。每个线程在尝试添加新节点时，首先在 `head[]` 数组上执行 `max()` 以确定当前的前驱节点，然后对该前驱节点的 `decideNext` 字段执行共识协议，最后将获胜节点写入自己的 `head[i]`。由于每次共识协议都会推进日志，新的头部节点最终一定会出现在 `head[]` 中。唯一可能导致某个线程永远无法添加自己节点的情况，是其他线程持续不断地成功添加节点——而这恰恰意味着系统整体在持续前进。因此，该构造满足无锁的定义。

## 4. 无等待的通用构造

如何将一个无锁算法改造为无等待算法？图 6.6 给出了完整的无等待算法。其关键保证在于：每个线程都必须在有限步数内完成 `apply()` 调用，即不允许任何线程被饿死。为此，算法允许正在推进的线程主动帮助那些未能取得进展的线程完成它们的调用。这种“相互帮助”的模式，在后续其他无等待算法中也会以类似的形式出现。

为了实现互帮互助，每个线程必须将自身正在执行的 `apply()` 调用公开给其他线程。为此，我们引入一个 n 元数组 `announce[]`，其中 `announce[i]` 表示线程 i 当前尝试挂入链表的节点。初始状态下，所有数组元素均指向序号为 1 的哨兵节点。当线程 i 将某节点存入 `announce[i]` 时，即表示该节点已被其宣告。

```java
public Universal {
    private Node[] announce;	// 用于协调帮助的数组
    private Node[] head;
    private Node tail = new Node();
    public Universal() {
        tail.seq = 1;
        for (int j = 0; j < n; j++) {
            head[j] = tail;
            announce[j] = tail;
        }
    }
    public Response apply(Invoc invoc) {
        int i = ThreadID.get();
        announce[i] = new Node(invoc);
        head[i] = Node.max(head);
        while (announce[i].seq == 0) {
            Node before = head[i];
            Node help = announce[(before.seq + 1) % n];
            if (help.seq == 0)
                prefer = help;
            else
                prefer = announce[i];
            Node after = before.decideNext.decide(prefer);
            before.next = after;
            after.seq = before.seq + 1;
            head[i] = after;
        }
        head[i] = announce[i];
        SeqObject myObject = new SeqObject();
        Node current = tail.next;
        whlie (current != announce[i]) {
            myObject.apply(current.invoc);
            current = current.next;
        }
        return myObject.aplly(current.invoc);
    }
}
```

<p align="center">图 6.6 无等待的通用构造</p>

线程在执行 `apply()` 时，首先宣告其新节点。这一步骤确保即使该线程自身无法将其节点挂入日志链表，其他线程也能代为完成。宣告之后，线程按原有流程继续尝试将节点加入链表：先读取一次 `head[]` 数组（第 15 行），然后进入主循环，循环持续直至其节点的序号变为非零，表明该节点已成功挂入链表（第 16 行检测）。

相比无锁算法，这里引入了一项改进：线程在循环中首先检查 `announce[]` 数组中是否有需要帮助的节点（第 18 行）。由于链表不断增长，需要动态确定需要帮助的节点。线程按照由 `seq` 对数组长度 `n` 取模所决定的递增次序，尝试帮助 `announce[]` 中的节点。可以证明，这种策略能保证任何靠自身无法推进的节点，在其拥有者线程的索引与 `max seq mod n` 匹配时，最终会得到其他线程的帮助。若省略这一帮助步骤，某个线程可能被其他线程无限次超越。若选中的节点无需帮助（例如其序号已非零，如第 19 行），则线程转而尝试将自身节点加入链表（第 22 行）。

`announce[]` 数组的所有元素初始均指向序号为 1 的哨兵节点。算法其余部分与无锁版本基本相同。一旦节点序号变为非零，即表示其已成功挂入链表，此时线程按先前方式，根据从链表尾部到自身节点的固定日志段计算结果。

图 6.7 展示了无等待通用构造的一个执行示例。初始状态下，线程 5 宣告其新节点并将其挂入日志链表，但在将该节点写入 `head[]` 数组之前暂停。随后线程 7 开始执行。由于 `(before.seq + 1) mod n` 的值为 2，而线程 2 并未尝试添加节点，因此线程 7 尝试挂入自己的节点。但线程 5 已在哨兵节点的 `decideNext` 共识中胜出，线程 7 在此轮竞争中落败。于是算法将完成线程 5 的操作，将线程 5 的节点序号设为 2，并写入 `head[]` 数组。

接下来，线程 3 宣告其节点后在进入主循环之前暂停。此时线程 7 转而帮助线程 3：将线程 3 的节点挂入链表并设其序号为 3，但在写入 `head[]` 数组之前暂停。随后线程 3 被唤醒，它不再进入主循环（因为其节点序号已非零），而是执行第 28 行，将节点写入 `head[]` 数组，并基于哨兵对象的副本计算其输出值。

![fig2](../static/images/multiprocessor-programming-chp-06/fig2.png)

对无锁算法的上述修改有一个精妙之处：由于多个线程可能同时尝试将同一个节点挂入日志链表，因此必须确保该节点不会被重复挂入两次。具体而言，一个线程可能在挂载某节点并设置其序号的同时，另一个线程也在试图挂载同一个节点并设置其序号。算法通过规定线程读取 `head[]` 数组最大值的次序以及 `announce[]` 数组中节点的序号，来避免此类错误。

设节点 `a` 由线程 A 创建，后被线程 A 和线程 B 先后挂入链表。在第二次挂入之前，`a` 必须已被至少写入 `head[]` 数组一次。此时，线程 B 从 `head[A]` 读取到的 `before` 节点（第 17 行）必然是 `a` 本身或 `a` 的后继节点。此外，任意节点在写入 `head[]` 数组（第 26 或 28 行）之前，其序号已被设为非零（第 25 行）。操作次序决定了：线程 B 必须先在第 15 或 26 行设置其 `head[B]`，然后才能在第 16 或 19 行检查 `a` 的序号是否非零（该检查取决于线程 A 或其它线程是否已执行该操作）。因此，第二次挂载的验证必然失败——因为节点 `a` 的序号已经非零，不会被再次挂入链表。

由于每个节点至多被挂入日志链表一次，且节点挂入的次序与方法调用之间的自然偏序（按时间先后）明显一致，因此该构造保证了线性一致性（linearizability）。

为证明该算法是无等待的，需要论证其互帮互助机制能保证：任一被宣告的节点最终都会被写入 `head[]` 数组（即进入日志链表），并且宣告该节点的线程能够完成其结果的计算。为便于证明，首先引入如下记号：记 `max(head[])` 为 `head[]` 数组中序号最大的节点；记 `c ∈ head[]` 表示存在某个线程 i，使得 `head[i]` 指向节点 `c`。

**辅助变量**（auxiliary variables，又称幻影变量，即 ghost variables）在代码中并不显式存在，也不会对程序的实际执行行为产生任何影响，其作用在于辅助我们对算法的行为进行推理。我们引入以下辅助变量：

* `concur(A)` 表示自线程 A 上一次宣告后，被写入 `head[]` 数组的节点集合。
* `start(A)` 表示线程 A 上一次宣告时，`max(head[])` 的 `seq` 值。

```java
public Response apply(Invoc invoc) {
    int i = ThreadID.get();
    < announce[i] = new Node(invoc); start(i) = max(head); concur(i) = {}; >
    head[i] = Node.max(head);
    while (announce[i].seq == 0) {
        Node before = head[i];
        Node help = announce[(before.seq + 1) % n];
        if (help.seq == 0)
            prefer = help;
        else
            prefer = announce[i];
        Node after = before.decideNext.decide(prefer);
        before.next = after;
        after.seq = before.seq + 1;
        < head[i] = after; (V j) (concur(j) = concur(j) U {after}); >
    }
    < head[i] = announce[i]; (V j) (concur(j) = concur(j) U {announce[i]}); >
    SeqObject MyObject = new SeqObject();
    Node current = tail.next;
    while (current != announce[i]) {
        MyObject.apply(current.invoc);
        current = current.next;
    }
    return MyObject.apply(current.invoc);
```

**引理 6.4.1**  对于所有的线程 A，下述断言总是成立的：
$$
|concur(A)| > n => announce[A] \in head[]
$$
**证明**  令 `a = announce[A]`。若 `|concur(A)| > n`，则 `concur(A)` 中包含两个连续的节点 `b` 和 `c`（分别由线程 B 和线程 C 挂入日志链表），且它们各自的序号加 1 后分别等于 `(A-1) mod n` 和 `A mod n`。这里需注意，线程 B 和 C 是实际将节点 `b` 和 `c` 挂入链表的线程，但不一定是宣告这两个节点的线程。

线程 C 在执行第 18 至 22 行时，会将 `announce[A]` 中的节点挂入日志链表，除非该节点已被挂入。我们需要证明：当线程 C 读取 `announce[A]` 时，线程 A 已经宣告了节点 `a`，因此线程 C 会将节点 `a` 挂入链表，或者节点 `a` 已被挂入。随后，当节点 `c` 被写入 `head[]` 数组且 `|concur(A)| > n` 时，根据引理，节点 `a` 必然已出现在 `head[]` 数组中。

为了理解为何在线程 C 执行第 18～22 行时节点 `a` 必定已被宣告，需注意以下两点：

1. 线程 C 将节点 `c` 挂入 `b` 之后，意味着它在第 17 行必然将 `b` 读为 `before` 节点；而在线程 C 从 `head[]` 中读取到 `b` 之前，线程 B 必定已经将 `b` 挂入日志链表。
2. 由于 `b` 属于 `concur(a)`，因此在线程 A 宣告 `a` 之后，`b` 才被写入 `head[]` 数组。

由 (1) 和 (2) 可知，线程 C 执行第 18～22 行之前，线程 A 已发出宣告。命题得证。
