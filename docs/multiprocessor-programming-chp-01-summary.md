<h1 align="center">多处理器编程的艺术</h1>
<h2 align="center">第一章 导论 总结</h2>

## 1. 时代背景

21 世纪初，芯片制造商渐渐无法制造出更小更快的处理器，开始转向**多核架构**（单个芯片上的多个处理器共享硬件缓存）。此后，随着摩尔定律 50 年统治生涯接近尾声，时钟速度增长大幅放缓。软件不能再依赖时钟频率自然提速，必须主动利用**并行性**来提高效率。

## 2. 核心挑战：异步性

现代计算机系统本质上是**异步的**：中断、抢占、缓存未命中、页面错误等事件会导致不可预测的延迟（从数十条指令到数亿条指令不等）。这使得多线程程序的协调远比串行程序复杂。

## 3. 基本原理 vs 实践应用

| 维度 | 内容 |
|------|------|
| **基本原理** | 可计算性理论、程序正确性（安全特性 + 活跃特性） |
| **实践应用** | 共享对象设计、性能分析、从自旋锁到事务性内存的渐进式工具集 |

- **安全特性**："坏的事情"永远不会发生（如互斥）
- **活跃特性**："好的事情"最终会发生（如无死锁、无饥饿）

## 4. 共享计数器与竞态条件

以素数打印任务为例：10 个线程从 1 到 10¹⁰ 中找出所有素数。简单平分输入范围无法均衡负载（素数分布不均、大数判定更慢）。更好的方案是引入一个**共享计数器**，每个线程从中取出一个数处理，处理完再取下一个：

```
i = counter.getAndIncrement();
```

然而，看似原子的 `value++` 在底层实际拆分为三步：读 value → temp + 1 → 写回 value。两个线程同时调用时，可能读到相同的值并写回相同的结果，导致计数器漏计（甚至倒退）。这一问题的根源在于对共享变量的**读取-修改-写入**并非原子操作。

解决该问题需要硬件提供的**读取-修改-写入指令**（如 Compare-and-Swap），或通过软件确保**互斥**——一次只有一个线程执行共享变量操作。这正是互斥问题产生的直接动机。

## 5. 三大经典协作问题

均以爱丽丝和鲍勃的寓言展开，形成递进关系：

### 5.1 互斥问题

- **场景**：爱丽丝的猫和鲍勃的狗不能同时在院子里
- **协议**：**旗帜协议**——每人一面旗，升旗后观察对方；冲突时鲍勃降下自己的旗帜，等待爱丽丝降旗，再重新升旗后放狗
- **特性**：
  - 互斥 ✓
  - 无死锁 ✓
  - 无饥饿 ✗（鲍勃可能饿死）
  - 等待（容错问题，一方拖沓则另一方阻塞）
- **关键结论**：互斥需要**持续通信**（而非瞬时通信，如呼喊/打电话）；两个 1-bit 变量（各自只写自己的、只读对方的）即可实现互斥

### 5.2 生产者-消费者问题

- **场景**：鲍勃投放食物，爱丽丝放宠物进食，双方不能同时在院子
- **协议**：**啤酒罐-绳子协议**——单比特状态机（up = 食物已空，down = 有待消耗的食物）
- **特性**：
  - 互斥 ✓
  - 无饥饿 ✓
  - 生产者-消费者语义 ✓（有食物才放宠物，食物未消耗完不投放）
- **与互斥协议的区别**：互斥要求无死锁（院子空时任意方可进入）；生产者-消费者假设持续合作

### 5.3 读者-写者问题

- **场景**：鲍勃写公告牌（一次一个字母），爱丽丝通过望远镜读
- **问题**：读写交错导致读到的信息混乱（如 "sell the" + "dog" = "sell the dog"）
- **解法方向**：无等待快照——读取时不阻塞写入，捕获瞬时一致快照
- **关键结论**：存在**无需等待**的解决方案（后续章节展开）

### 5.4 问题特性对比

| 特性 | 互斥 | 生产者-消费者 | 读者-写者 |
|------|------|--------------|----------|
| 互斥 | ✓ | ✓ | 读者间不互斥 |
| 无死锁 | ✓ | ✓ | — |
| 无饥饿 | ✗ | ✓ | — |
| 需等待 | ✓ | ✓ | ✗（无等待解法存在）|
| 持续通信 | ✓ | ✓ | — |

## 6. 阿姆达尔定律

$$ S = \frac{1}{1 - p + \frac{p}{n}} $$

- S：加速比；p：可并行化比例；n：处理器数
- **核心启示**：即使 90% 可并行化（p=0.9），在 10 核机器上加速比也仅为约 5x
- 串行部分的粒度必须尽可能小（如计数器示例中将互斥范围限制在 getAndIncrement 调用内）
- **完全并行问题**（如某些科学计算/图形处理）很少出现在系统中

## 7. 方法论：逐步求精

1. **理想化数学模型**：关注可计算性与正确性，学习如何在假设条件下推理并发算法
2. **现实体系结构**：考虑缓存、总线等硬件细节，设计真正高效的算法与数据结构
3. 先掌握经典互斥算法的数学证明（虽不实用，但训练推理能力），再评估实际多核架构下的方案

> **全书定位**：为程序员提供一套工具和技术，使其能够妥善处理代码中依赖协作与同步的部分——这部分代码的优化对整体性能影响深远。

## 8. 总结

第一章作为全书的导论，为多处理器程序设计建立了完整的问题框架：

1. **为什么需要多处理器编程** — 摩尔定律终结，单核性能增长放缓，必须转向并行计算获取性能提升。

2. **核心困难是什么** — 系统异步性导致线程交错不可预测；共享数据的并发访问需要精细协调；性能建模（阿姆达尔定律）表明串行部分对加速比有不成比例的拖累。

3. **三大基础协作问题** — 互斥、生产者-消费者、读者-写者是并行协调中三类最基本的协作问题。通过爱丽丝与鲍勃的寓言，展示了每个问题所需满足的特性（安全/活跃）及其协议设计的权衡（等待 vs 无等待、公平性 vs 吞吐量）。

4. **全书路线图** — 从理想化数学模型出发训练推理能力，再过渡到现实体系结构下的高效设计，循序渐进地覆盖理论与实践两个层面。

本章的核心洞见在于：**串行部分的质量决定了并行系统的上限**——无论是阿姆达尔定律中的加速比瓶颈，还是互斥协议中等待时间的影响，都指向同一个结论：协调与同步是多处理器程序设计的决定性因素。
