<h1 align="center">多处理器编程的艺术</h1>
<h2 align="center">第三章 并发对象 总结</h2>

## 1. 引言

以基于锁的 FIFO 队列为例——每个方法在执行期间持有互斥锁，方法调用严格按顺序执行，容易验证其正确性。然而，阿姆达尔定律指出这种粗粒度加锁会严重限制并发性。因此，需要一套不依赖方法级锁定的方案来描述和分析并发对象的行为。

本章核心议题：并发对象的**正确性条件**（安全）和**演进条件**（活跃）。

## 2. 串行对象与顺序规范

- **串行对象**的行为由**前置条件**和**后置条件**描述，称为**顺序规范说明**
- 顺序规范只需关注每次方法调用之前和之后的对象状态（通过副作用来简洁描述方法间的交互），而调用过程中的任何中间状态都可以安全忽略
- 多线程环境中，重叠的方法调用使"对象状态"的概念变得模糊——方法调用时必须面对不完全的对象状态

## 3. 三种正确性条件

### 3.1 顺序一致性（Sequential Consistency）

**定义**：存在一个全序排列所有方法调用，使得：
1. 每个线程的调用次序与**程序次序**一致
2. 该全序符合对象的**顺序规范说明**

**关键性质**：
- ✗ **不保持实时次序**：一个方法调用在另一个开始时已完成，仍可能被重新排序
- ✓ **非阻塞**：任何挂起的完全方法调用都可立即找到一个满足顺序一致性的响应
- ✗ **不可组合**：多个顺序一致的对象组合后，整体可能不满足顺序一致性

> 顺序一致性适合描述独立系统（如硬件存储器接口）。

### 3.2 线性一致性（Linearizability）

**定义**：每个方法调用在其**调用事件和响应事件之间的某个时刻**立即生效（称为**可线性化点**）。即保持**实时次序**：若方法 A 在 B 开始前已完成，则 A 必须在 B 之前生效。

**关键性质**：
- ✓ **保持实时次序**
- ✓ **非阻塞**
- ✓ **可组合**：若干可线性化对象组合后仍然是可线性化的

> 仅通过共享单个对象通信的线程无法区分顺序一致性与线性一致性。只有能够观察到操作之间实时次序的外部观察者，才能判断一个顺序一致的对象是否不可线性化。

### 3.3 静态一致性（Quiescent Consistency）

**定义**：仅当对象处于**静态**（无挂起方法调用）时，强制方法调用按实时次序执行。

**关键性质**：
- ✗ **不保持程序次序**（非静态间隔内可任意重排）
- ✓ **非阻塞**
- ✓ **可组合**
- 与顺序一致性**不可比较**（存在满足其一而不满足另一的执行）

> 类比抢座位游戏：音乐播放期间任意活动，音乐停止（静态）时所有挂起调用必须返回一个共同满足顺序规范的结果。适用于对次序要求宽松的高性能场景（如索引分发）。

### 3.4 三种条件对比

| 特性 | 顺序一致性 | 线性一致性 | 静态一致性 |
|------|-----------|-----------|-----------|
| 保持程序次序 | ✓ | ✓ | ✗ |
| 保持实时次序 | ✗ | ✓ | 仅静态间隔 |
| 可组合 | ✗ | ✓ | ✓ |
| 非阻塞 | ✓ | ✓ | ✓ |
| 适用场景 | 独立系统 | 大规模组合系统 | 高性能宽松系统 |

## 4. 形式化定义

基于**历史记录**（history）的精确描述：

- **方法调用** = 一次**调用事件** + 后续的匹配**响应事件**（若未返回则为挂起）
- **顺序历史记录**：调用与响应交替出现，无重叠
- **顺序规范说明**：对象合法顺序历史记录的集合

**线性一致性的形式化**：历史记录 H 是可线性化的，当且仅当存在一个合法顺序历史记录 S，使得：
1. `complete(H)` 可通过将一些挂起调用扩展到完成状态得到 H'
2. S 是 H' 的一个排列，且保持 H' 中所有非重叠调用间的 → 关系

**定理 3.6.3**：H 是可线性化的 ⇔ 对每个对象 x，H|x 是可线性化的（可组合性）。

**定理 3.6.4**：线性一致性是非阻塞的——任何挂起的完全方法调用都可以立即响应而不破坏线性一致性。

## 5. 内存一致性模型

将共享内存视为一个由多个寄存器组成的单一对象。其正确性特性称为**内存一致性模型**。

- 早期的多处理器假设内存是顺序一致的
- 现代硬件和编译器可能对读写进行重新排序（出于性能优化），大多数情况下不保证顺序一致性
- 通过同步原语（如 volatile）抑制重排序——本书第一部分为清晰展示算法思想省略了这些声明，第二部分在实际代码中将包含它们

## 6. 演进条件

正确性条件例如线性一致性的非阻塞特性保证任何挂起的方法调用都有一个正确的响应。但是正确性条件并没有说明如何计算这样的响应，甚至根本没有要求提供实现方法来生成一个响应。

演进条件是并发系统的一种**活跃特性**，它要求提供具体的实现方法来生成对挂起调用的响应，规定了在什么情况下方法调用能够在有限步骤内完成。

### 6.1 演进条件谱系

```
演进条件 ──────┬── 非阻塞 ────┬── 无等待（每个线程，独立于调度）
               │             ├── 无锁（某线程，独立于调度）
               │             └── 无阻塞（某线程，需独立执行）
               │
               └── 阻塞 ──────┬── 无饥饿（每个线程，需公平调度）
                             └── 无死锁（某线程，需公平调度）
```

### 6.2 演进条件详述

| 条件 | 谁演进 | 调度依赖 | 含义 |
|------|--------|----------|------|
| **无等待** | 每个线程 | 独立 | 线程只需自身被执行，有限步内完成 |
| **无锁** | 某线程 | 独立 | 系统整体演进，个别线程可能饥饿 |
| **无阻塞** | 某线程（独立执行时） | 需独立执行 | 若独立执行（无其他线程干扰），有限步内完成 |
| **无饥饿** | 每个线程 | 需公平调度 | 每个有挂起调用的线程最终都能完成 |
| **无死锁** | 某线程 | 需公平调度 | 有挂起调用的线程在执行时，某个方法调用能在有限步内完成 |

### 6.3 演进条件三维分类

| 维度 | 分类 |
|------|------|
| **演进范围** | 最大演进（所有线程可行进）vs 最小演进（某线程可行进） |
| **阻塞性** | 阻塞（延迟影响其他线程）vs 非阻塞（延迟不影响其他线程） |
| **调度依赖性** | 独立（不依赖调度假设）vs 非独立（依赖公平调度或独立执行） |

- 无等待、无饥饿、无阻塞 → 最大演进
- 无锁、无死锁 → 最小演进
- 无等待、无锁 → 独立
- 无阻塞、无饥饿、无死锁 → 非独立

### 6.4 阻塞演进条件

第 2 章中锁算法的无死锁/无饥饿属于阻塞演进条件，依赖两条假设：
1. 持有锁的线程在有限步骤后释放锁
2. 调度程序允许持有锁的线程继续执行

若临界区抢占罕见，阻塞条件与非阻塞条件差距不大；若抢占频繁，应使用非阻塞演进。

## 7. 评析

**选择正确性条件**：

| 应用 | 推荐条件 |
|------|----------|
| 打印服务器（次序无关） | 静态一致性 |
| 银行转账（保持程序次序） | 顺序一致性 |
| 股票交易（公平、按到达顺序） | 线性一致性 |

**选择演进条件**：取决于对底层平台的假设强度。
- 假设越少（如无等待），实现开销越高
- 可接受更强假设（如公平调度），可实现更廉价的解决方案
- 不同方法可采用不同演进条件（如频繁调用的查表方法用无等待，少调用的更新方法用互斥）

## 8. 总结

第三章为并发对象的规范与标准建立了完整的理论框架——正确性条件规定"何为正确"，演进条件规定"能否完成"。这一框架为后续章节提供了统一的叙述语言和分析工具：

1. **三种正确性条件**：线性一致性强于顺序一致性和静态一致性，但后两者之间不可比较（存在非静态一致的顺序一致执行，反之亦然）。
2. **演进条件**从强到弱：无等待（最强）→ 无锁 → 无阻塞 / 无饥饿 → 无死锁（最弱）。六种条件构成一个由独立最大演进到非独立最小演进的谱系。
3. **关键洞察**：正确性条件和演进条件是**正交**的——可线性化的对象不一定无等待，无等待的对象也不一定可线性化。实际设计中需要根据应用需求在两者之间做权衡。
