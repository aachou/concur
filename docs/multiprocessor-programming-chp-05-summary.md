<h1 align="center">多处理器编程的艺术</h1>
<h2 align="center">第五章 同步操作原语的相对能力 总结</h2>

## 1. 主题与核心思想

本章研究：设计多处理器时应支持哪些原子同步指令？全章用 **共识数**（consensus number）这一概念为同步原语"打分"，并证明这些原语构成一个能力层级。

**核心度量**：一种原语类的共识数 = 用它能解决共识问题（多个线程对同一个值达成一致）的**最大线程数**。

- 共识数 = 1：约等于没法用，只能一人拍板。
- 共识数 = 2：能协调两个线程，三人不行。
- 共识数 = 无限：多少人都能协调，这就是"王者指令"。

**为什么用共识来打分？** 因为共识衡量了同步对象解决多线程共识问题的能力。无法用一个共识数较低的同步对象无等待地构造出共识数更高的同步对象（推论 5.1.3：若 C 可由 D 实现，则 C 的共识数 ≤ D 的共识数）。根据共识数，我们就可以分析一个同步对象究竟能不能用一个同步原语来实现。

## 2. 共识性基础

**共识对象**：只提供一个方法 `decide(v)`，满足两条性质：

- **一致性**：所有线程选同一个值。
- **有效性**：选中的值必须是某个线程的输入。

**无等待实现**中，由于每个线程只调用一次 decide() 且线程数有限，无锁实现等价于无等待实现。以无等待方式实现共识的类称为**共识性协议**。

**关键引理**（理解所有证明的前提）：

- 每个共识协议都有**二价**（bivalent）的初始状态：结果未定，取决于读写交错。
- 每个共识协议都有**临界状态**（critical）：处于二价，但任何线程再走一步都会使状态变为单价。

**证明套路（全章通用）**：假设某个对象类能解决 N 线程共识 → 让协议跑到临界状态 → 根据该对象的"记号能力"构造两个不同的执行顺序，它们分别把结果推向 0 和 1，但**从某个线程的角度看两个状态长得一模一样** → 该线程无法做出不同决策 → 矛盾。

## 3. 各原语共识数一览

| 同步原语 | 共识数 | 为什么 |
|---|---|---|
| 原子寄存器 | **1** | 写是覆盖式（后写擦掉先写）、读只改本地不留痕 → 刻不出"谁先谁后" |
| FIFO 队列、栈、优先队列、列表、集合 | **2** | 能钉死顺序（谁先出队谁赢），但做不了 3 线程 |
| 非平凡 RMW 寄存器 | ≥2 | 函数非恒等即可（f(v)≠v 的哨兵值） |
| Common2 RMW（getAndSet / getAndIncrement / getAndAdd） | **恰为 2** | 函数可交换或可重写，输家无法识别赢家身份 |
| 多重赋值 (n, n(n+1)/2) | 有限，随 n 增长 | 成对字段可恢复全序，但字段数平方增长 |
| **compareAndSet (CAS)** | **无限** | 赢家编号永久唯一可查 |

### 3.1 原子寄存器（共识数 = 1）

双线程证明（定理 5.2.1）：在临界状态下，A、B 的下一步只可能是"读 / 写不同寄存器 / 写同一寄存器"三种情况。每种情况都能构造两种执行顺序，使共享内存的最终画面完全相同，但协议要求一个定 0 一个定 1 —— 线程被迫在相同画面前做出不同决策，矛盾。

**核心因果链**：做共识必须依赖"留在共享内存里、且不会被抹掉的先后痕迹"。寄存器写会覆盖、读不留痕 → 任何顺序的最终画面都一样 → 无法区分谁先谁后。

**推论 5.2.2**：任何共识数 > 1 的对象，都无法用原子寄存器实现。因为实现是"降级或平级"操作，能力不可能凭空涨。这意味着：光靠 load/store 永远写不出无锁并发数据结构，硬件必须提供同步原语。

### 3.2 队列、栈等（共识数 = 2）

**正面（至少 2）**：用一个队列做双线程共识。初始化入队 WIN、LOSE（WIN 在前）。各线程把答案写进共享数组后出队：出队拿 WIN 者赢（返回自己答案），拿 LOSE 者输（返回对方答案）。FIFO 顺序天然保证 WIN 先被取出。

**反面（最多 2）**：三线程场景下，临界状态中 A、B 的下一步只有三种可能（入队+入队 / 入队+出队 / 出队+出队），每种都构造两个对第三方 C 不可区分的状态 → 矛盾。队列能区分的"先后信息"最多区分一对——赢家和输家，当有两个输家时，它们分不清谁才是真正的赢家。

### 3.3 多重赋值对象

- **(m,n)-赋值**：在 n 个格子中原子地同时写 m 个。是原子快照（一次读多个）的对偶，但强得多——快照能用寄存器实现（共识数 1），多重赋值不能。
- **n 线程推广 (n, n(n+1)/2)-赋值**：字段为 n 个私有 $r_i$ + C(n,2) 个成对 $r_{ij}$，线程 i 一次原子写 $r_i$ 和所有 $r_{ij}$（共 n 个格子）。
  - 每个线程只赋值一次 → n 个赋值事件有真实时间全序。
  - 成对字段 $r_{ij}$ 终值 = 后写者的标记（两人都写完后再没人动它）→ 是"擦不掉的先后刻度"。
  - 拼合成对比较可恢复全序；第一个赋值者 X 是赢家，X = 唯一一个"自己的所有成对字段都被别人覆盖"的线程，所有人算出同一个 X，取 $r_X$ 的值。
  - **读序纪律**：读不是原子的，须先读所有私有字段判定"谁已赋值"，再读这些线程的成对字段，才能读到终值。
  - 边界：共识数最多为 n，无法解 n+1 线程。

### 3.4 RMW 操作与 Common2（共识数 = 2）

**RMW（读取-修改-写入）**：原子地"读当前值 v → 按函数 f 变换 → 写回 → 返回旧值"。如 `getAndSet(v)`、`getAndIncrement()`、`getAndAdd(k)`、`compareAndSet(e,u)`、`get()`。

**非平凡 RMW（函数非恒等）共识数 ≥ 2**：把寄存器初始化为 v（f(v)≠v），各线程做 RMW，旧值 == v 者即第一个碰它的人 → 赢。注意 `rmw()` 不带参数，函数对所有线程固定。

**Common2 的局限**（可交换或可重写）：

- **可重写**（swap 等常数函数）：所有写入产生同一个常数 c，寄存器只有 v / c 两个状态，是一块"二元标记牌"，不编码任何身份。
- **可交换**（fetch_add 等）：最终值 = 初始 + 总和，顺序不影响结果。

**精确表述**：输家只能确定"自己不是第一个"，区分不了名次、也识别不了赢家身份；2 线程时靠排除法（总共两个人）能推出赢家，3 线程时排除不掉 → 共识数卡在 2。

### 3.5 compareAndSet（共识数 = 无限）

`compareAndSet(expected, update)`：值等于 expected 才替换并返回 true，否则不动返回 false。

**n 线程共识协议**：寄存器初始化为 FIRST（不等于任何线程编号）。各线程把答案写进数组后，一起 `compareAndSet(FIRST, 自己的编号)`：返回 true 者是唯一把值从 FIRST 换掉的人 → 赢；返回 false 者读寄存器拿到**赢家的编号** → 取赢家答案。

**CAS 的独特之处**：函数既不可交换也不可重写，而是"**条件性覆盖**"——只有第一个人能成功，写进去的是赢家自己的编号，之后无人能再改写。对比之下 swap 的写入不携带身份信息（可重写），fetch_add 的结果不携带顺序信息（可交换），而 **CAS 把"赢家编号"永久、唯一、可查地刻在寄存器里**。

**推论**：仅支持 CAS 的寄存器共识数即为无限（get 仅为方便，非必需）。

## 4. 关键证明套路

全章证明都是同一方法：**假设能解 N 线程共识 → 让协议跑到临界状态 → 根据对象的"记号能力"构造两个执行顺序，结果分别指向 0 和 1，但某个线程无法区分这两个状态 → 矛盾**。

两种"无法区分"的来源：

- **没留下痕迹**（寄存器）：写覆盖、读不留痕，任何顺序画面相同。
- **痕迹不携带身份/顺序**（Common2）：所有写入结果相同，或顺序不影响结果。

## 5. 结论

- **推论 5.2.2**：任何共识数 > 1 的对象都无法用原子寄存器实现 → 硬件必须提供同步原语，才能支撑无锁并发数据结构。
- 原语能力层级：寄存器(1) < 队列/栈/集合/Common2(2) < 多重赋值(随 n 增长) < **CAS(无限)**。
- 支持 CAS 的机器与"串行图灵机 + 异步化"的机器等价：任何可实现的并发对象都能无等待实现。故书中引 Maurice Sendak 之言：**"compareAndSet 是万物之王。"**
